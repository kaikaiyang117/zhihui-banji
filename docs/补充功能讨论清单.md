# 高中教师与班主任补充功能开发执行清单

> 文档性质：Agent 开发执行规格，而不是功能创意备忘录。
>
> 适用对象：高中任课教师、高中班主任，以及负责本项目实现、测试和验收的开发 Agent。
>
> 使用原则：本文件只描述已经讨论并确认的补充方向。Agent 必须先读本文件和项目规范，再按工作包逐项实现；不得因为“看起来有用”而自行增加未列出的模块。

## 0. Agent 使用说明

### 0.1 开始任何实现前必须读取的资料

1. `AGENTS.md`：项目分层、隐私、数据库、渠道和测试约束。
2. 本文件：功能范围、实现效果、验收标准和明确不做的内容。
3. `docs/系统功能开发计划.md`：确认当前允许开始的系统工作包及依赖顺序。
4. `docs/Agent能力矩阵.md`：涉及 Agent 工具、权限、微信渠道时，确认登记要求。
5. `DESIGN.md`：项目视觉语言和设计 token 的权威来源。
6. `docs/补充功能界面设计规范.md`：涉及网页、手机、微信交互或桌面宠物时，按其中的入口、状态、响应式和视觉验收要求执行。
7. 与当前工作包相关的现有服务、路由、页面和测试；优先复用，不复制业务逻辑。

如果本文件和代码现状不一致，先以代码和测试为事实依据，并在开发说明中指出差异；不要静默改变产品范围。若差异会改变数据模型、权限、对外发送或用户工作流，必须暂停并请求确认。

### 0.2 每个工作包的固定实施顺序

除非工作包明确说明是纯页面能力，统一按以下顺序执行：

1. **确认现状**：定位已有数据表、服务、API、页面、Agent 工具和测试。
2. **业务服务**：在 `server/src/services/` 实现唯一业务逻辑；服务不得依赖 Agent、微信或前端。
3. **数据与迁移**：确需新增表或字段时，在 `server/src/db/schema.ts` 增加兼容迁移；不直接修改真实数据库。
4. **系统 API**：在 `server/src/http/routes/` 暴露最小接口，沿用现有权限、班级和学期上下文。
5. **网页 UI**：先写清界面合同，再按 `docs/补充功能界面设计规范.md` 复用现有 Vue 组件、路由和 `frontend/src/api.js`；前端构建产物必须写入 `backend/static/`。
6. **Agent 工具/渠道**：只有业务服务和 API 可独立工作后，才评估网页 Agent 或微信 iLink 接入；工具权限、敏感等级和渠道范围同步登记。
7. **验证与文档**：完成自动化测试、人工场景验证、`git diff --check`，再更新本文件状态、系统功能开发计划和能力矩阵。

### 0.3 工作包完成定义

一个工作包只有同时满足以下条件才能标记为“已完成”：

- 用户目标在网页端（以及该工作包声明的微信/Agent 渠道）可以走通完整闭环。
- 业务服务可独立调用，业务逻辑没有复制到路由、Vue 组件或渠道适配器。
- 写入操作有权限校验、明确确认、幂等或撤销策略；只读操作有班级/学期范围。
- 空数据、歧义、错误输入、重复提交、过期确认和依赖服务失败都有可理解的提示。
- 新增界面覆盖加载、空、有数据、校验失败、服务失败、无权限、只读和提交中状态，并完成桌面/手机截图与真实交互验证。
- 相关后端测试、前端构建和需要的 UI/微信/Electron 冒烟验证通过。
- 没有把真实学生、家长或健康数据写入日志、测试夹具、截图或提交记录。
- `docs/系统功能开发计划.md`、`docs/Agent能力矩阵.md`（如涉及 Agent/微信）和本文件状态已同步。

### 0.4 状态和优先级

- **已确认，待开发**：范围已经确认，可以按顺序进入开发，但尚未完成实现和验收。
- **开发中**：已有明确任务正在实现；其他 Agent 不得并行扩大范围。
- **已完成**：达到本文件的完成定义，并有验证证据。
- **暂不开发**：明确排除，不得作为“顺手功能”加入。
- **待确认**：存在会改变产品范围的关键选择，先讨论，不得写代码假设。

### 0.5 本轮已确认的产品决策

以下决策已经由产品负责人确认，后续 Agent 可以据此执行，不要再次把它们当成待确认项：

- **目标角色**：以“高中政治老师兼班主任”为首要示例用户。数据模型和权限不能写死政治学科；任课教师可跨年级、跨多个班级，班主任可管理所负责班级。通知、课程、考试和家长会示例优先使用政治学科/班主任场景，其他学科沿用同一流程。
- **功能范围**：`SUP-01` 至 `SUP-09` 全部允许进入路线图；仍按 P0/P1/P2 顺序和依赖交付，不得因为“全部允许”而并行创建重复入口或跳过前置服务。
- **使用渠道**：网页桌面、局域网手机网页、微信 iLink 和 Electron 桌面宠物均可以纳入设计，但每个工作包必须按本清单声明实际支持的渠道。允许评估不等于每个渠道都必须第一版上线：网页是业务基线，手机优先覆盖现场操作/图片上传，iLink 优先覆盖短指令/确认，宠物只做状态反馈。
- **角色素材**：允许使用用户提供的动漫人物图片制作“美美”桌面宠物。正式开发前把图片复制到持久的 `design-assets/` 或等价目录并记录来源与使用授权；临时会话路径只用于参考，不能写入代码、构建配置或发布包。
- **证据留痕**：涉及请假、家校沟通、学生事件和教育处理的工作，优先保存原始图片/截图并保留关联、来源、哈希和审计信息；截图不能自动变成学生事实或家长承诺。

如果后续讨论只涉及实现细节（例如图标、按钮文案、动画帧率），不需要重新打开上述产品决策；如果要改变角色、渠道、权限或数据范围，必须在第 14 节追加变更记录。

## 1. 总体产品边界

### 1.1 面向人群和场景

本工作台主要服务高中场景：

- 任课教师：可能同时承担多个年级、多个班级的教学和日常事务；首要示例为同时教授政治课的老师。
- 班主任：首要示例为政治老师兼班主任，需要处理考勤、家校沟通、班级通知、个别学生跟进和家长会准备。
- 典型设备组合：办公室电脑运行本地工作台，课堂、走廊、宿舍等现场使用微信 iLink 或手机浏览器。

### 1.2 必须保持的系统边界

- 运行时数据仍以本地 SQLite 为准；知识库仍为本地 Markdown；Excel 是导入/导出格式，不是运行时数据库。
- 局域网手机访问只适用于可信局域网；微信 iLink 需要办公室电脑和后端持续在线，第一版不做离线同步。
- 业务服务是学生、成绩、考勤、课程、考试、沟通和报告等事实的唯一实现位置。
- 请假、沟通和教育处理等需要说明过程的业务记录，应能关联原始图片/截图证据；证据文件和业务记录必须可相互追溯。
- Agent 负责理解、规划、调用工具和解释结果，不能直接操作 SQLite，也不能在 Prompt 中复制业务规则。
- 家长通知第一阶段只生成、编辑、复制和人工核对，不自动发送到微信群或家长个人。
- 不保存外部网站密码，不抓取外部网站，不把外部系统嵌入工作台，不承诺统一登录。
- 桌面宠物属于可关闭的桌面体验层，只表达工作状态和打开工作台；宠物异常不得影响后端、主窗口和真实业务数据。

### 1.3 明确暂不开发的功能

以下项目从本批次中移除，后续 Agent 不得重新加入：

- 作业布置、作业收交和催交统计。
- 监考安排、阅卷安排和监考日历。
- 教学进度管理与备课提醒。
- 班级周工作计划。

## 3. SUP-01：现场移动操作与微信 iLink

### 3.1 要解决的问题和最终效果

教师在教室点名、宿舍查寝时通常不在办公室，电脑和手机也不在同一局域网。完成后应达到：

- 教师可以在微信中发起短指令，不需要打开复杂网页或携带电脑。
- 系统能识别当前授权教师，并要求明确班级、日期、场景和写入范围。
- 点名采用“默认全到，只补录异常”的短流程，避免在手机上逐个填写全班名单。
- 写入前给出人类可读的预览；教师明确确认后才写入。
- 重复确认不会重复新增记录；网络中断、凭证过期或后端离线时给出明确失败原因。

第一版的基本依赖是办公室电脑、后端服务和 iLink 持续在线。不要承诺“手机离线后先记、回办公室自动同步”。

### 3.2 功能范围和交互流程

#### A. 教室点名

最小流程：

1. 教师发送“开始点名”或从 iLink 快捷菜单进入。
2. 若教师有多个班级，先列出授权班级；只有一个班级时可默认该班，但仍在预览中显示班级名称。
3. 默认日期为业务日期；跨日或补录历史日期时必须让教师确认日期。
4. 选择场景：早读、第一节、课间、晚自习或自定义场景。场景名称必须来自业务服务允许值。
5. 系统读取该班级当前学生范围，提示“默认全到，可回复异常学生和状态”。
6. 教师输入异常，例如“张三迟到，李四请假”。系统解析学生和状态，无法唯一匹配时先追问。
7. 返回预览：班级、日期、场景、总人数、正常人数、异常名单、缺失信息。
8. 教师回复“确认”后调用现有考勤批量服务；返回成功数量、更新数量和失败行。

#### B. 宿舍查寝

第一版只保留流程设计和权限边界，是否开放写入需要结合现有宿舍数据服务确认。若开放，流程应为：

1. 选择查寝批次/日期和授权宿舍范围。
2. 只展示完成查寝所需的最小学生或宿舍信息。
3. 快速记录在寝、未归、晚归、请假等允许状态。
4. 返回预览并要求确认，再以批量事务提交。
5. 宿舍信息、健康信息和家庭信息不得因为“方便点名”自动暴露给微信会话。

#### C. 现场只读查询

第一版允许查询：

- 今日课程和教室。
- 今日临时调课/停课/活动。
- 近期考试日期和科目。
- 当前教师待办摘要（仅返回必要字段）。

不允许通过 iLink 默认查询完整成绩单、家庭住址、家长电话、健康档案或全班长期行为档案。

### 3.3 实现要求

- 复用 `WeChatService → AgentRunner → 工具 → 业务服务` 链路；微信适配器不得直接访问数据库或复制点名逻辑。
- 点名写入必须复用现有 `saveDailyAttendance` 批量事务和唯一键语义；如果现有服务不支持场景字段，先在服务层补齐，不在微信路由中拼 SQL。
- 所有写工具登记名称、参数、只读/写入属性、敏感等级、允许渠道、是否需要确认、对应业务服务和测试。
- 写入确认沿用现有 Agent 操作状态机：预览生成参数哈希，确认窗口 10 分钟失效（如现有实现已规定其他时长，以代码为准），确认只能应用同一份预览。
- 微信会话使用 `wechat:{微信用户}` 命名空间；不得与网页会话共享 ID。
- 消息去重、审计、有限重试和断线恢复复用现有机制；审计只记录参数摘要，不记录完整学生/家长隐私。
- 当前项目仅解析文字消息。图片消息的解析、下载、暂存和证据关联由 `SUP-08` 统一实现；`SUP-01` 只调用已经完成的证据服务。语音或位置仍需另列工作包。

### 3.4 验收标准

- [ ] 一个授权教师可以从 iLink 完成单班级点名的“发起—补充异常—预览—确认—结果”闭环。
- [ ] 多班级教师未明确班级时，系统不会猜测或写入错误班级。
- [ ] 学生姓名不唯一、状态不合法、日期缺失时会追问或拒绝写入，不静默修正。
- [ ] 同一预览重复确认只产生一次有效业务结果，审计中能看到重复请求被幂等处理。
- [ ] 未授权微信用户、过期确认、后端离线、iLink 凭证过期都有可理解提示。
- [ ] 宿舍流程若未完成权限和服务验证，必须保持关闭，而不是以临时接口上线。
- [ ] 网页点击点名、网页 Agent 和 iLink 调用同一业务服务，结果一致。

### 3.5 验证方式

自动化：

- 补充点名参数解析、班级歧义、确认过期、重复确认和权限测试。
- 补充微信登录、消息收发、会话隔离、断线恢复和审计测试。
- 运行：

```bash
cd server
npm run typecheck:server
npm run test:server
npm run build:server
```

人工/集成：

1. 使用临时数据创建一个教师、两个班级和若干学生；分别完成正常点名、含迟到/请假点名和补录历史日期。
2. 重复发送确认、发送错误班级、使用未授权微信账号，检查无错误写入。
3. 在确认窗口过期后确认，检查系统要求重新生成预览。
4. 停止后端或断开 iLink，再恢复服务，检查失败提示和会话恢复。
5. 验证桌面工作台的点击入口和两个 Agent 渠道结果一致。

## 4. SUP-02：对话式 Excel 导入助手

### 4.1 要解决的问题和最终效果

用户不必先判断“应该去哪个模块”、下载哪个固定模板或记住列名。用户在网页 Agent 对话框（后续可扩展 iLink）上传 Excel 后，系统应：

- 先识别和预览，绝不因上传文件而立即写入业务数据。
- 能解释工作表、表头、字段映射、班级/学期范围、新增/更新/跳过/错误行。
- 遇到多个可能模块、缺少学号、字段歧义或目标不明确时，先提问。
- 用户明确确认后，调用已有导入服务原子提交，并支持幂等和错误行修正。
- 固定模板入口继续保留，作为可靠后备和批量失败恢复入口。

首批只支持已有稳定导入服务的四类数据：学生、成绩、校历、课程表。不得以“通用 Excel Agent”为名一次性支持任意业务表。

### 4.2 标准流程

1. 接收 `.xlsx` 文件，保存到带所有者、渠道、会话和过期时间的临时目录，计算 SHA-256。
2. 读取文件大小、工作表名称、表头、行数和脱敏样例；阶段一不调用写入服务。
3. 使用确定性的表头别名、工作表结构和当前上下文判断候选模块。模型可以解释候选，但不能绕过确定性校验直接选择。
4. 若候选唯一，询问或读取必要的班级/学期/导入模式；若候选不唯一，列出选项并暂停。
5. 调用对应业务服务生成预览，包括：
   - 字段映射和未识别列；
   - 有效行、错误行、重复行数量；
   - 新增/更新/跳过数量；
   - 班级、学期和日期范围；
   - 可能覆盖或合并的字段；
   - 错误行及人类可读原因。
6. 在对话中展示预览，要求用户明确确认；取消、修改目标或重新上传会使旧预览失效。
7. 确认后使用现有批次、事务和 `request_id` 幂等机制提交。
8. 返回成功摘要、失败行下载/导出入口和下一步建议；过期后清理临时文件和预览状态。

### 4.3 网页与微信渠道要求

- 网页端先实现上传控件、文件元数据传递、预览卡片、确认/取消按钮和错误行下载。
- iLink 协议是否能在当前接入配置中收到 `file_item` 文件消息，必须以实际协议实现、官方说明和脱敏消息 fixture 的核验结果为准；不能只因为协议类型名存在就宣称“支持 Excel 附件”。当前项目只解析文字消息，因此第一版网页上传是确定基线，iLink 文件属于单独的接入任务。实现 iLink 文件时，必须完成文件消息解析、CDN 下载、AES 解密、临时文件落盘和大小/超时校验，再接入同一导入流水线；若任一环节未验证，明确返回“请在网页端上传”，不把附件当作文本或静默丢弃。
- 网页上传和 iLink 下载后的文件必须使用同一个识别、预览、确认和提交服务，不得维护两套导入规则。
- iLink 只返回适合短消息的摘要；完整错误行通过网页端或本地文件入口获取，不把长表格塞进微信消息。

### 4.4 数据、安全和错误边界

- Agent 工具不能直接操作 SQLite；不得把整份 Excel、完整错误行或学生隐私写入模型会话摘要和普通审计日志。
- 临时文件记录至少包含所有者、渠道、会话、哈希、文件大小、创建时间、过期时间和当前预览状态；不得将真实文件长期存入知识库。
- 第一阶段只接受项目已有解析能力明确支持的 `.xlsx`；密码保护、宏文件、损坏文件、超大文件和不支持的 `.xls` 必须明确拒绝并说明原因。
- 一个文件只允许对应一个明确导入目标；不能“试着导入学生，失败后再试成绩”而不重新确认。
- 预览必须显示重复策略；无法确定是合并、更新还是新增时，必须暂停询问。
- 错误行下载必须使用临时、受保护的本地入口，不能生成公开链接。

### 4.5 验收标准

- [ ] 用户上传学生、成绩、校历、课程表样例文件时，系统能进入正确预览流程，不直接写入。
- [ ] 表头别名、缺少学号、重复行、空日期和多工作表歧义都有稳定结果。

## 6. SUP-04：多班级教师视角

### 6.1 功能解释和最终效果

“多班级教师视角”指任课教师同时教高一多个班、高二多个班时，可以在一个页面汇总查看自己负责班级的课程和考试安排，避免反复切换班级。它不是全校管理员视角，也不是把所有班级数据开放给所有教师。

最终效果：

- 教师明确配置或选择自己负责的班级集合。
- 在“我的课程/考试”视图按日期汇总多个班级，并显示班级标签。
- 同一时间多个班级冲突、同一科目多班考试等情况可被看见。
- 任何写入（调课、考勤、成绩、通知对象选择）仍要求明确单个班级；汇总视图默认只读。

### 6.2 前置决策和最小实现

开始编码前必须确认项目当前是否有教师账号与教师—班级关系。如果没有，第一版只能采用本地工作台配置的“我的班级列表”，不能从课程表文本推断所有权。

最小可行方案：

1. 在设置或班级上下文中维护当前教师的班级集合。
2. 汇总读取现有课程表和考试服务，所有结果附带班级、年级和学期。
3. 提供筛选班级、日期和年级的只读页面；不改变原有单班级页面。
4. Agent 查询必须先读取当前教师班级集合；集合为空或目标不明确时追问。

### 6.3 验收标准

- [ ] 一个教师配置两个以上班级后，可以在一个页面看到所有选中班级的课程和考试。
- [ ] 结果始终显示班级标签、日期和学期；相同课程/考试不会被无标识地合并。
- [ ] 未配置、已移除或非授权班级不会出现在汇总结果。
- [ ] 从汇总结果进入写入操作时必须回到单班级上下文并再次确认。
- [ ] 原有单班级页面、导入和课程解析功能不受影响。

### 6.4 验证方式

准备一个教师、两个年级和三个班级的临时数据，验证班级配置、筛选、同日多班、空集合和移除班级；尝试从汇总视图发起写操作，确认系统阻止无班级目标的写入。完成后运行后端全量测试、前端构建和主要页面 UI 冒烟。

如果教师—班级关系、账号权限或班级配置入口尚未确定，工作包状态保持“待确认”，不得先写一个不可持续的隐含规则。

## 8. SUP-06：家校通知/家校沟通模板一键复制

### 8.1 要解决的问题和最终效果

家长沟通的痛点不是“再增加一张回访表”，而是教师每次都要重新组织措辞、容易漏掉时间和行动要求。参考用户提供的界面，第一版做成“场景模板卡片 + 可编辑的微信通知文案区”：

- 左侧选择场景模板，右侧生成可编辑文案。
- 模板使用变量（称呼、放假时间、返校时间、考试时间、携带材料等），缺失变量必须醒目提示。
- 教师可以直接修改、复制到微信，再自行核对和发送。
- 可以把编辑后的内容另存为个人模板。
- 不记录回访日期、家长承诺和完成结果；不自动生成家校沟通台账记录。

### 8.2 首批场景和明确不做

首批场景建议固定为：

- 放假/返校通知。
- 安全提醒（交通、居家、网络等）。
- 调课/考试安排通知。
- 班级活动或研学通知。
- 材料收集/学习安排提醒。

不要在没有确认的情况下增加缴费通知、家长承诺跟踪、回访日历、完成率统计或群发功能。用户已明确作业收交不做，因此“学习安排提醒”只表示通知模板，不是作业收交模块。

### 8.3 实现要求

- 新增独立的模板业务服务，在现有 `/parent-comm` 中增加“通知模板”页内视图；侧边栏继续只保留一个“家校沟通”，不要把通知草稿混入沟通台账的事实记录。
- 模板至少包含：名称、场景、正文、变量定义、是否系统模板、所有者、更新时间和启用状态。
- 变量应声明必填/选填、显示标签和格式规则（日期、时间、班级名称等）；生成前进行确定性校验。
- “生成文案”可以调用 Agent 做语言润色，但事实字段、日期和对象必须由业务服务提供；模型不能自行编造考试时间或学生事实。
- 网页端支持场景卡片、变量表单、正文编辑、恢复模板、复制、另存为个人模板和清空。
- iLink 第一阶段只返回短文案或提示教师到网页复制；不自动向班级群、家长个人或第三方平台发送。
- 发送前提示再次核对时间、对象和隐私；当前版本不提供发送按钮。

### 8.4 验收标准

- [ ] 选择每个首批场景都能生成可编辑、变量已替换的文案。
- [ ] 必填变量缺失时不能生成“看似完整”的文案，提示具体缺项。
- [ ] 文案可编辑、复制、恢复原模板和另存为个人模板；刷新后模板仍可用。
- [ ] 生成/复制不会自动写入家校沟通台账，不会产生回访、承诺或完成记录。
- [ ] Agent 生成的日期、考试和班级信息来自工具结果；没有数据时会提示补充，不会臆造。
- [ ] iLink 不会触发家长群或个人消息发送。

### 8.5 验证方式

自动化覆盖模板 CRUD、变量格式和缺失校验、模板权限、复制内容、个人模板隔离、台账不被污染、Agent 工具权限和 iLink 不发送。

人工验证：

1. 选择“放假通知”，填写用户提供的日期和返校时间，检查生成内容与截图中“关键消息清单”结构一致且可继续编辑。
2. 故意漏填日期、填写无效日期或选择错误班级，检查阻止生成或明确提示。
3. 修改生成文案并另存为个人模板，刷新后重新使用。
4. 检查数据库中没有新增回访日期、家长承诺或完成结果字段/记录。
5. 在网页和 iLink 分别生成文案，确认都只提供草稿，不发送。

## 10. SUP-08：图片/截图证据留痕

### 10.1 要解决的问题和最终效果

教师的很多工作不仅要“完成”，还要能在事后说明依据和处理过程。最典型的是学生请假：只有一条“请假”考勤记录不足以回答“谁提出、何时提出、原始说明是什么”，需要保留家长请假截图、纸质假条照片或证明材料。

本工作包完成后应达到：

- 请假、家校沟通、学生事件和教育处理记录可以关联一张或多张原始图片/截图。
- 业务页面显示“有证据/无证据”和附件数量，可以预览缩略图、查看原图、下载原图及查看上传信息。
- 每张证据都记录关联对象、上传人、上传时间、来源渠道、原始文件名、文件大小和 SHA-256，能够发现文件被意外替换或损坏。
- 原图不被裁剪、压缩或覆盖；展示使用单独生成的缩略图，原始文件始终保留。
- 删除或替换证据必须留下原因和审计记录，不能无痕修改历史。
- 数据迁移包和恢复流程包含证据原图，并在恢复后校验文件与元数据一致。

这里的“证据”是教师工作的内部留痕，不宣传为司法取证、电子签名或法律意义上的可信时间戳。

### 10.2 当前实现基础和复用要求

项目已经存在以下局部附件能力：

- `class_task_attachments`：班级任务材料，使用本地文件、原子写入、SHA-256 和按班级/学期下载校验。
- `fund_attachments`：班费凭证，使用本地文件、原子写入、SHA-256 和审计。
- `activity_attachments`：活动材料，使用本地文件、原子写入、SHA-256 和权限范围校验。
- `server/src/services/files.ts`：提供安全路径解析、原子写入、SHA-256 和临时文件清理。
- 系统迁移包已经包含业务附件和知识库文件。

开发时必须复用上述文件安全能力和存储约定。第一阶段不强制把班级任务、班费和活动附件迁移到新表；先保证既有功能继续可用，并为请假、沟通、学生事件等缺少附件能力的模块建立统一证据服务。若以后统一既有附件表，应单独设计兼容迁移和回滚，不在本工作包顺手重构。

### 10.3 第一阶段覆盖范围

#### A. 请假与考勤（第一优先级）

- 考勤状态为“请假”时，记录页面提供“上传请假凭证”。
- 支持家长微信请假截图、短信截图、纸质假条照片和其他图片证明。
- 图片关联到具体 `attendance_record`，同时保留学生、班级、学期和考勤日期范围，不能只挂在学生名下而失去业务上下文。
- 允许先保存请假记录再补传凭证；页面应提示“请假记录尚无凭证”，但第一版不强制所有请假必须上传图片。
- 如果通过微信 iLink 收到图片，系统先暂存，询问学生、请假日期/时段和原因，生成“请假记录 + 图片证据”预览；教师明确确认后才写入和关联。

#### B. 家校沟通

- 允许给一条既有家校沟通记录补充聊天截图或家长反馈截图。
- “生成通知”“复制通知”和“已发送通知”不等于存在发送证据；只有教师上传截图并确认关联后，页面才显示“有发送/沟通凭证”。
- 截图可能包含其他学生、群成员昵称和头像，上传前提示教师裁剪或避免无关隐私；系统不自动把截图内容写入沟通摘要。

#### C. 学生事件与教育记录

- 允许给需要说明处理过程的学生事件或教育记录附加现场照片、书面说明截图和处理结果图片。
- 附件只证明“保存了该材料”，不能由 Agent 自动推断责任、处分或学生评价。

#### D. 既有附件模块

- 班级任务材料、班费凭证和活动附件继续使用现有接口。
- 补充统一的迁移完整性验证：导出后再导入临时目录，逐个核对数据库元数据、文件存在性和 SHA-256。
- 如果统一展示“证据数量”，可以在读取层汇总既有附件，但不得复制文件或创建第二份事实记录。

### 10.4 数据模型和文件存储要求

新增统一证据元数据时，建议使用独立的 `evidence_attachments` 表，至少包含：

| 字段 | 含义和约束 |
|---|---|
| `id` | 证据记录 ID |
| `class_id`、`term_id` | 权限和数据范围；必须与关联业务记录一致 |
| `owner_type`、`owner_id` | 关联对象类型与 ID；类型只能来自服务端白名单 |
| `student_id` | 可选的学生关联，便于学生时间线查询；不能代替业务关联 |
| `evidence_kind` | 请假截图、沟通截图、现场照片、证明材料等受控分类 |
| `original_name` | 用户上传时的文件名，仅作展示，不参与路径拼接 |
| `stored_name`、`relative_path` | 随机存储名和数据目录内的安全相对路径 |
| `mime_type`、`size_bytes` | 经文件内容校验后的真实类型和大小 |
| `sha256` | 原始文件哈希；用于下载、迁移和恢复完整性校验 |
| `source_channel` | `web`、`wechat`、`mobile_web` 等明确来源 |
| `note` | 教师填写的简短说明，不由 OCR 自动生成事实 |
| `created_by`、`created_at` | 上传人和服务器时间 |
| `deleted_at`、`deleted_by`、`delete_reason` | 软删除和删除理由；支持审计与恢复 |

`owner_type` 第一阶段只允许 `attendance`、`communication`、`student_event` 和代码实际确认存在的教育记录类型。服务必须先验证关联记录存在、班级/学期一致且当前用户有权访问，再保存文件。

文件存储规则：

- 原图写入 `WORKBENCH_DATA_DIR` 下的受控附件目录，不存入 SQLite BLOB，也不存入知识库。
- 使用随机存储名和 `safeResolve`，原始文件名不得成为可执行路径。
- 文件先在临时目录完成大小、真实格式和哈希检查，再原子移动到正式目录；数据库事务失败时清理正式文件，文件失败时不写入元数据。
- 第一版支持 JPEG、PNG、WebP，每张图片最大 10MB；类型以文件内容为准，不能只相信扩展名或客户端 `Content-Type`。
- HEIC、GIF、SVG、PDF 和其他文件第一版明确拒绝并给出转换提示。若以后支持，需另补安全解析、预览和测试。
- 原始图片不做重新编码，不覆盖已有文件。缩略图是可删除重建的派生文件，不作为证据原件。
- 同一业务记录上传相同 SHA-256 时提示重复并要求确认；微信重复投递必须通过消息 ID 和文件哈希幂等处理。

### 10.5 网页和手机端交互

相关业务记录详情页增加统一“证据与附件”区域：

1. 显示证据数量、缩略图、类型、上传时间、来源和说明。
2. 支持文件选择、拖拽和剪贴板粘贴截图；局域网手机页面支持调用相册/相机。
3. 上传后先显示本地预览和文件信息，用户选择证据类型、填写可选说明并确认关联。
4. 点击缩略图打开受权限保护的原图预览；提供下载原图和查看完整性信息。
5. 删除需要二次确认和填写原因；进入回收状态后业务记录仍显示“曾有证据，现已删除”。
6. 提供“有证据/无证据”筛选，方便班主任检查请假记录是否缺少凭证。

上传控件必须可用于桌面和手机窄屏。证据区域不能把所有截图一次性加载为原图，应先加载缩略图，打开时再读取原图。

### 10.6 Agent 与微信 iLink 规则

- 新增证据能力时，业务服务先提供保存暂存图片、确认关联、列出元数据、读取受权原图、软删除和恢复能力。
- Agent 工具默认只读取证据元数据和数量，不把原图或 OCR 文本自动塞入模型上下文。
- 网页 Agent 可接收用户主动上传的图片，但必须先展示关联对象预览，再请求确认。
- 微信 iLink 接入图片前，先依据实际协议实现图片消息识别、下载、解密、大小限制和临时文件清理；不得把未经校验的远程地址直接登记为证据。
- 仅发送图片、没有文字说明时，Agent 必须追问“对应哪个学生、哪一天、什么事项”；不能通过图片内容猜测并直接写入请假。
- OCR 或视觉识别不在第一阶段范围。以后如果增加，识别结果只能作为“待核对提取文本”，必须由教师确认后才能进入业务字段。
- 微信会话中只返回图片已暂存、待关联、已关联等最小状态；不要主动回传完整敏感截图。

### 10.7 修改、删除、备份和恢复规则

- 证据原件不可原位替换。上传错图时，先软删除旧证据并记录原因，再上传新证据，两个动作都进入审计。
- 业务记录被软删除时，证据保持关联并随记录进入回收状态；恢复业务记录后证据重新可见。
- 自动清理只作用于未确认的暂存图片；已关联证据不自动过期。
- 物理清除已关联证据必须是单独的高风险操作，明确目标、原因和备份状态；本工作包第一版不提供批量物理删除。
- 数据库备份、迁移包导出和迁移包导入必须包含正式证据文件。恢复后逐个校验路径、大小和 SHA-256，并报告缺失、损坏和多余文件。
- 导出业务表时默认只输出证据数量和本地受控引用，不把敏感图片嵌入普通 Excel；如需证据包，另行显式导出。

### 10.8 验收标准

- [ ] 请假考勤记录可以上传一张或多张 JPG/PNG/WebP，刷新后仍可查看缩略图和受权原图。
- [ ] 证据元数据与请假记录的学生、班级、学期和日期一致，不能跨班级/学期错误关联。
- [ ] 上传空文件、伪造扩展名、超过 10MB、危险路径和不支持格式时拒绝写入，且不留下孤立文件或元数据。
- [ ] 原图下载后 SHA-256 与上传时一致；缩略图生成、删除或重建不改变原图哈希。
- [ ] 同一业务记录重复上传相同图片会提示；微信重复投递不会生成多份证据。
- [ ] 删除必须填写原因并进入审计，原记录可恢复；系统不存在无痕覆盖原图的入口。
- [ ] 家校通知只有上传并确认截图后才显示“有凭证”，生成或复制草稿不会被误判为已发送。
- [ ] Agent 无法仅凭图片直接创建请假或处分事实，必须获得学生、日期、事项和用户确认。
- [ ] 迁移包导出并导入临时数据目录后，证据数量、业务关联和 SHA-256 全部一致。
- [ ] 既有班级任务、班费和活动附件上传/下载流程保持通过。

### 10.9 验证方式

后端自动化至少覆盖：

- 图片签名、MIME、大小、空文件和路径穿越校验。
- 原子写入失败、数据库事务失败和暂存过期清理，不产生孤立文件。
- 允许的 `owner_type`、不存在的关联记录、跨班级/学期和未授权访问。
- SHA-256、同记录重复图片、微信消息重复投递和确认幂等。
- 软删除、删除原因、恢复、业务记录回收/恢复联动和审计摘要。
- 迁移包导出/导入后的文件存在性、大小和哈希完整性。
- 既有 `class_task_attachments`、`fund_attachments`、`activity_attachments` 回归。

前端和人工验证至少覆盖：

1. 在考勤页面新增一条请假记录，分别通过文件选择、拖拽和粘贴上传截图。
2. 在局域网手机页面拍照/选择图片，确认窄屏预览、上传状态和失败重试可用。
3. 给家校沟通记录上传截图，验证“有凭证”只由真实关联证据触发。
4. 使用其他班级上下文和未授权设备请求原图，确认返回拒绝而不是暴露文件路径。
5. 软删除图片、恢复图片、删除业务记录并恢复，核对证据状态和审计。
6. 导出迁移包，在隔离临时目录导入，逐张下载并校验哈希。
7. 如果本工作包同时接入 iLink，用授权账号发送一张无文字图片，确认系统先追问；补充学生和日期并确认后再建立关联。

执行后端全量测试、前端构建和 UI 冒烟；涉及 iLink 时同时执行微信和 Agent 测试，涉及迁移包时运行对应迁移集成测试。

### 10.10 第一阶段明确不做

- 不做自动 OCR 入库、自动识别请假人、自动判断真假或自动生成处分结论。
- 不做图片编辑、美化、涂改或覆盖原图；如需遮挡隐私，由教师在上传前处理。
- 不做公开分享链接、云相册、微信群自动抓取或家长端主动上传门户。
- 不承诺司法级存证、区块链存证、可信时间戳或电子签名。
- 不支持任意文件类型，也不提供无限容量和批量物理删除。

## 11. SUP-09：“美美”桌面宠物与工作状态反馈

### 11.1 产品定位和最终效果

桌面宠物暂定名称为“美美”，形象来源于用户提供的原创动漫人物：长卷黑发、黑色椭圆眼睛、珍珠耳饰和手链、米白色黑波点无袖上衣、牛仔短裤、白色运动鞋，整体为温暖的手绘蜡笔/水彩贴纸风格。

它不是独立聊天机器人，也不是新的业务模块。它是 Electron 桌面端的轻量状态反馈层：

- 工作台启动时友好打招呼。
- Agent 正在处理任务时显示专注/冲刺状态。
- 等待教师确认或补充信息时显示询问/等待状态。
- 操作成功时短暂显示“收到/完成”反应。
- 操作失败时显示沮丧或生气反应，并由工作台正文提供具体错误信息。
- 空闲较久或到达休息时间时显示困倦状态。
- 点击宠物可以唤起已隐藏的主工作台；用户可以拖动、隐藏、调整大小或完全关闭。

宠物只显示通用状态和短句，不显示学生姓名、成绩、家长信息、健康情况或沟通原文。宠物渲染失败、素材缺失或窗口崩溃时，主窗口、后端、托盘和 Agent 必须继续可用。

### 11.2 已提供素材评估

用户本次提供 11 张 `1254×1254` PNG，其中两张“我 emo 了”内容重复。素材包括一张九宫格表情参考，以及打招呼、冲刺、困倦、收到、生气、沮丧、下班和安抚等单张动作图。

当前素材的客观限制：

- 文件是 RGB PNG，没有透明通道，白色背景已合成进图片。
- 大部分单图包含中文文字、白色贴纸边、爱心、星星、云朵和情绪符号。
- 部分动作只有半身，人物比例、服装细节和发型在不同图片间存在轻微差异。
- 单张静态图没有动画中间帧，不能直接组成自然循环。

因此这些图片作为“角色身份、表情和动作参考”，不直接作为最终宠物帧。最终素材应保留角色外观和手绘质感，同时去除背景、文字和脱离人物的装饰；提示文字由桌面宠物 HTML 气泡单独渲染，避免缩小后模糊，也方便无障碍、国际化和状态替换。

参考动作与运行状态映射：

| 参考内容 | 建议运行状态 | 使用方式 |
|---|---|---|
| 九宫格表情 | 表情和语气基准 | 提取挥手、点赞、收到、疑问、困倦、查看和完成等面部/手势特征 |
| 全身抱臂图 | 角色比例基准 | 作为全身轮廓、服装、鞋子和饰品参考，另生成中性站姿 |
| “嗨”挥手 | `waving` | 启动、重新显示宠物时播放一次 |
| “冲鸭”奔跑 | `running` / `running-right` / `running-left` | Agent 工作中和宠物被拖动后的移动反馈 |
| “困困了” | `sleep` / 长空闲 | 夜间或长时间无交互时使用 |
| “收到”点赞 | `success` | 写入、导入或操作成功后短暂播放 |
| “气鼓鼓”与“我 emo 了” | `failed` | 错误或任务失败；不替代正文错误提示 |
| “下班啦” | 退出/隐藏反馈 | 用户主动隐藏或退出工作台前短暂播放；不阻塞退出 |
| “给你个台阶” | `waiting` / `review` | 等待确认、预览结果或需要用户决定时使用 |

开始正式资产制作前，必须把用户确认的原始图片复制到持久的设计素材目录；当前会话临时路径不能写入代码、清单或构建配置。用户拥有这些原创角色素材的使用权这一前提应在资产任务记录中注明。

### 11.3 技术方案选择

第一版采用“精灵图动画 + Electron 独立透明窗口”，理由如下：

- 静态 PNG 加 CSS 摇摆开发最快，但状态动作单一，达不到类似 Codex 桌面宠物的完整反馈效果。
- Live2D 需要分层 PSD、头发/手臂/眼睛等独立部件和骨骼变形参数；当前是合成后的平面 PNG，重新拆件和绑定成本高，且容易破坏手绘质感。
- 透明序列帧/精灵图可以保留原画风格，状态机简单、离线运行、跨 macOS/Windows 一致，也便于做确定性的帧尺寸和透明度验证。

资产格式建议采用兼容 Codex v2 宠物的图集约定：

- 每格 `192×208`，8 列、11 行，最终图集 `1536×2288`。
- 第 0–8 行依次为 `idle`、`running-right`、`running-left`、`waving`、`jumping`、`failed`、`waiting`、`running`、`review`。
- 第 9–10 行提供顺时针 16 个注视方向，用于宠物在空闲时轻微看向鼠标；用户启用“减少动态效果”时关闭注视跟随。
- `pet.json` 保存稳定 ID、显示名称、描述、`spriteVersionNumber: 2`、图集路径和帧率配置。

采用这个约定可以直接复用成熟的资产生成、拼装和 QA 流程。执行环境存在 `hatch-pet` skill 时，资产制作必须按该 skill 完成基础形象、九个标准状态、十六方向、透明背景、动画预览、视觉 QA 和 v2 打包；skill 不可用时，先说明阻塞，不用未经验证的手工切图冒充最终图集。

### 11.4 资产生产要求

资产制作分四步，每一步完成标准清晰可检查：

1. **锁定角色身份**：以全身图和九宫格为主参考，产出一张中性、完整、无文字、无背景、无悬浮装饰的标准全身图。完成条件是发型、脸、波点上衣、短裤、鞋和饰品均与参考一致，缩小到宠物实际尺寸仍可识别。
2. **生成标准状态**：为九个标准状态分别生成连贯循环；每行保持相同人物比例、基线、发型、服装和配色。完成条件是逐行预览没有裁切、比例跳变、背景残留或身份漂移。
3. **生成注视方向**：先确认上、右、下、左四个方向，再补齐 16 个方向。人物眼睛先移动，头部和上身轻微跟随，脚和下半身保持稳定；不旋转整个人物图层。完成条件是四个主方向在实际显示尺寸下可分辨，连续方向没有突然跳动。
4. **拼装和校验**：生成透明 WebP 图集、`pet.json`、状态联系表、动图预览和联系表。完成条件是尺寸、透明度、帧数、方向、循环和视觉 QA 全部通过。

美术约束：

- 所有文字从角色帧移除；“收到”“困困了”等文案由气泡组件渲染。
- 角色外的爱心、星星、云朵、速度线和大面积白色贴纸边默认移除。成功/失败状态优先用姿势和表情表达。
- 允许保留珍珠耳饰、珍珠手链、紫色手镯等角色身份配件；所有帧中左右位置和数量保持一致。
- 透明背景必须真实透明，白色背景不能用近白色伪装；头发边缘不得出现明显白边。
- 循环动作保持克制：空闲以呼吸、眨眼和轻微发丝摆动为主，避免持续大幅跳动影响教师办公。

### 11.5 Electron 窗口架构

在现有 `desktop/main.js` 管理一个独立 `petWindow`，不把宠物 DOM 塞进主 Vue 页面：

- 使用无边框、透明、不可缩放、默认置顶和不显示任务栏的 `BrowserWindow`。
- 宠物页面使用独立的 `desktop/pet/index.html`、样式和渲染脚本；通过专用 `pet-preload.js` 暴露最小 IPC。
- 保持 `nodeIntegration: false`、`contextIsolation: true`、`sandbox: true` 和 `webSecurity: true`；宠物渲染层不能读取文件系统、完整 `ipcRenderer` 或任意后端接口。
- 宠物页面只加载打包内的本地资源，拦截所有导航和新窗口；外部链接能力不向宠物暴露。
- `electron-builder.yml` 明确打包宠物页面、专用 preload、图集和清单；开发和打包模式使用同一资源定位函数。
- 应用退出时关闭宠物窗口；宠物窗口被用户隐藏或崩溃不触发后端退出，也不改变主窗口生命周期。

窗口默认靠近当前主显示器右下角但不遮住系统任务栏/Dock。使用 Electron `screen.getDisplayMatching()` 和 `workArea` 约束位置；拖动后保存相对于显示器工作区的位置，显示器拔出、分辨率变化或缩放变化时重新夹入可见区域。

### 11.6 交互和设置

第一版交互保持最小：

- 拖动角色移动位置。
- 单击显示/收起短气泡；双击显示并聚焦主工作台。
- 右键菜单提供：打开工作台、暂时隐藏、置顶开关、大小、减少动态效果、重置位置、关闭桌面宠物。
- 托盘菜单增加“显示/隐藏桌面宠物”，设置页增加是否启用、开机显示、大小、置顶、气泡和减少动态效果。
- 默认静音，不加入音效；首次升级不强制弹出宠物，由用户在一次性介绍中选择是否开启。
- 透明区域尽量点击穿透，人物可交互区域接收拖动和点击；使用 `setIgnoreMouseEvents(..., { forward: true })` 时必须分别在 macOS 和 Windows 验证鼠标转发，不能让透明窗口大面积挡住桌面操作。

第一版宠物固定在用户选择的位置，不在整个桌面自动游走。空闲注视鼠标只做头眼微动，不跟踪键盘内容、不截屏、不读取当前应用窗口。

### 11.7 状态控制和工作台联动

在 Electron 主进程增加单一 `petStateController`，接收经过白名单校验的状态事件，避免主页面、Agent 页面和宠物页面各自维护一套状态。建议优先级：

```text
failed > waiting > review > running > success > reminder > idle > sleep
```

状态规则：

- `running`：用户发送 Agent 请求、导入解析或工具执行开始；任务结束后退出。
- `review`：正在生成预览、验证导入、整理摘要或等待系统校验。
- `waiting`：Agent 需要用户确认写入、选择班级或补充必要参数；保持到确认、取消或会话失效。
- `success`：操作成功后播放一次，约 2–3 秒后回到 `idle`，连续成功事件合并，避免频繁跳动。
- `failed`：确定失败后播放一次，气泡只显示“操作没有完成，请到工作台查看原因”等通用提示。
- `reminder`：近期考试等轻提醒每天最多主动出现一次；不在课堂演示/勿扰时段弹出。
- `sleep`：长时间空闲或用户设定的休息时段；有新任务立即唤醒。

主窗口通过现有 preload 新增受限 IPC 上报枚举状态和事件 ID；主进程拒绝未知状态和包含学生数据的自由文本。宠物不直接调用 AgentRunner、不持有 API Key、不订阅完整审计轨迹，也不自行执行写工具。点击宠物只唤起主工作台，所有确认和业务操作仍在现有页面或 Agent 对话中完成。

为防止闪烁，控制器需要最短展示时间、同事件幂等、优先级抢占和回落状态。主窗口刷新、隐藏或渲染进程重启后，宠物应恢复到最近有效状态或安全回到 `idle`，不能永久卡在“处理中”。

### 11.8 数据、隐私和故障隔离

- 宠物设置和屏幕位置保存在 Electron `userData`，不写入业务 SQLite，也不随班级/学期切换。
- 气泡只接收预定义文案 key 和非敏感计数；禁止传入学生姓名、学号、成绩、联系方式、健康信息和完整错误堆栈。
- 不记录鼠标轨迹、当前窗口标题、键盘输入、桌面截图或用户打开的软件。
- 动画资产完全离线，不从远程 CDN 加载，不在运行时调用图片生成服务。
- 宠物窗口创建失败时只写入脱敏桌面日志并禁用本次宠物，不弹出循环错误框，不阻塞工作台启动。
- 开启系统“减少动态效果”或用户设置后，改为静态帧或低频眨眼；窗口隐藏/屏幕锁定时暂停动画计时器。

### 11.9 验收标准

- [ ] 最终角色在常用显示大小下能稳定识别为用户提供的动漫人物，所有状态保持相同发型、脸、服装和配件。
- [ ] 图集为 `1536×2288` 的透明 PNG/WebP，单元格 `192×208`，`pet.json` 使用 `spriteVersionNumber: 2`，标准状态和 16 个注视方向通过资产校验。
- [ ] 图集中没有烘焙文字、白色方形背景、裁切身体、跨格内容、明显白边或不一致角色。
- [ ] 主窗口隐藏时宠物仍可显示；双击宠物能恢复并聚焦主窗口。
- [ ] 用户可以拖动、隐藏、关闭、调整大小和重置位置；重启后设置保持，显示器变化后窗口仍在可见工作区。
- [ ] 透明区域不会明显阻挡桌面点击，角色拖动和右键菜单在 macOS、Windows 均可用。
- [ ] Agent 的处理中、预览、等待确认、成功和失败能映射到正确状态；重复事件不重复播放，状态优先级和回落正确。
- [ ] 宠物气泡和 IPC 中不出现学生、家长、成绩或健康敏感信息。
- [ ] 禁用宠物、素材损坏或强制关闭宠物渲染进程时，主窗口、托盘、后端和 Agent 继续正常工作。
- [ ] 隐藏宠物和屏幕锁定后动画停止；空闲状态不存在持续高频网络请求或后端轮询。

### 11.10 验证方式

资产验证：

- 检查最终图集尺寸、帧占用、透明背景、空单元格和 `pet.json` 版本。
- 生成九个标准状态的循环预览、完整联系表和“中性帧 + 16 方向”检查表。
- 在真实显示尺寸检查身份一致性、动作含义、方向、基线、裁切和动画跳变；失败行整行修复，不拼贴风格不同的单帧。

Electron 自动化/集成测试至少覆盖：

- 启用时只创建一个 `petWindow`，禁用和无素材时不创建。
- 窗口安全选项、导航拦截、专用 preload 白名单和退出清理。
- 显示/隐藏、主窗口唤起、位置持久化、屏幕边界夹取和托盘菜单。
- 状态优先级、同事件幂等、短暂状态回落、渲染重启恢复和敏感字段拒绝。
- 宠物渲染进程崩溃时主工作台和后端健康检查仍通过。

人工验证至少在一台 macOS 和一台 Windows 设备完成：

1. 在普通屏、Retina/高 DPI、双显示器和任务栏/Dock 不同位置下检查显示比例与位置。
2. 拖动宠物、点击宠物周围透明区域、使用右键菜单，确认不遮挡正常桌面操作。
3. 依次触发 Agent 处理中、等待确认、成功和失败，核对状态、文案、停留时间和回落。
4. 隐藏主窗口、锁屏、睡眠唤醒、拔出副显示器、关闭宠物和退出应用，检查生命周期。
5. 开启减少动态效果和勿扰设置，确认动画和提醒按设置收敛。

涉及代码实现时运行前端构建和 Electron 冒烟测试；如果状态事件来自 Agent 页面，同时运行后端 Agent 测试和网页 Agent 的主要交互冒烟。

### 11.11 第一阶段明确不做

- 不做 Live2D 骨骼、3D 模型、语音、音效、摄像头、麦克风和情绪识别。
- 不做多宠物、换装商城、养成数值、签到奖励和班级积分游戏化。
- 不让宠物自动在多显示器间奔跑，不使用全局键盘钩子，也不读取其他软件内容。
- 不在宠物气泡中完成学生数据查询、写入确认或复杂 Agent 对话；第一版点击后回到主工作台处理。
- 不在运行时生成图片或联网下载皮肤；所有发布资产在构建前完成 QA 并随 Electron 安装包分发。

## 13. 当前明确不做和防止范围膨胀的规则

- 不把本清单扩展成“全能教务系统”。外部教务、教学平台和家校平台只通过 `SUP-05` 做快捷入口。
- 不因为支持 iLink 就增加完整手机端、云端同步或公网反向代理。
- 不因为支持对话式 Excel 就允许模型直接写数据库或接收任意未知业务表。
- 不因为增加证据留痕就把截图内容自动识别为学生事实；证据上传、业务记录和人工确认必须分开。
- 桌面宠物保持为可关闭的状态反馈层，不扩展成第二套聊天窗口、业务入口或养成系统。
- 不因为做家校模板就增加群发、自动发送、家长承诺跟踪、回访日历和完成率统计。
- 不因为做家长会准备就自动生成学生评价或替教师下结论。
- 不重新加入作业、监考/阅卷、教学进度/备课提醒和班级周工作计划。
- 任何新增想法都先进入“待确认”，写清楚高中教师/班主任痛点、最小范围、数据来源、权限和验收方式，得到确认后才能变成新的 `SUP-xx` 工作包。

## 17. 收口审阅结论

本清单当前已经覆盖本轮确认的业务范围、高中角色、渠道边界、证据留痕、桌面宠物、界面合同和逐项验收。后续实现时优先关注以下三类容易偏离的地方：

1. **课程表是基础上下文**：考试倒计时、多班级视角、通知变量和现场查询都优先复用班级/学期课程与校历，不各自再造日期体系。
2. **证据是横向能力**：请假先落地，但家校沟通、学生事件和既有附件模块必须保留统一的关联、权限、哈希、软删除和迁移校验语义。
3. **界面保持收敛**：新功能优先放入已有页面的页内视图；首页只加近期考试等高频摘要；桌面宠物只做状态反馈，不形成第二套业务入口。

如果后续出现新想法，先按第 13 节的范围膨胀规则和第 15 节确认项评估；只有明确痛点、数据来源、权限、最小闭环和验收证据后，才新增工作包。
